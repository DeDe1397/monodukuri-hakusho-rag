# ものづくり白書 相談チャットボット

商工会議所の経営指導員が、中小製造業からの経営相談に対応する際に、
「令和5年度 ものづくり基盤技術の振興施策」（ものづくり白書）から
業界動向・課題認識・支援策を**根拠付き（章・ページ）で**引けるようにするRAGチャットボット。
検索して終わりではなく、面談メモ・提案メモの下書き生成まで行う。

動作そのものより**設計判断の説明可能性**を重視して作っている。
そのため中核ロジック（PDF解析・チャンク分割・検索・スコア統合）はすべて自作し、
ブラックボックスを残していない。

## 想定ユースケース

- 利用者: 商工会議所の経営指導員
- 場面: 中小製造業との面談で、白書に基づく業界動向・支援策をその場で調べたい
- 質問例: 「中小企業の賃上げ状況は？」「DX人材育成の支援策は？」
  「人手不足とDXの両方に悩む企業に紹介できる支援策は？」（複数章にまたがる相談型）
- 出力: 出典（章・節・ページ）付きの回答、および面談メモの下書き

## アーキテクチャ

```
data/raw/*.pdf
      │  pdf_loader.py  … ページ単位でテキスト・章節ラベル・図表キャプションを抽出
      ▼
  ページ辞書のリスト
      │  chunker.py      … 章節境界→段落→文→文字数 の優先順位で階層分割（自作）
      ▼
  チャンクのリスト (id, text, page, section, figures)
      │  embedder.py      … OpenAI Embeddings をバッチ呼び出し→L2正規化→保存（自作）
      ▼
  data/processed/{chunks.json, vectors.npy}
      │
      ▼
  retriever.py  … ベクトル検索/BM25/ハイブリッド(RRF) をnumpyだけで自作
      │
      ▼
  generator.py  … 出典付きプロンプト組み立て・閾値ゲート・LLM呼び出し（自作）
      │
      ▼
  pipeline.py（検索＋生成を束ねる薄い層）
      │
      ▼
  app.py（Streamlit: チャット / メモ下書き）
```

## 設計判断とその理由

### なぜ外部ベクトルDB（Chroma/FAISS等）を使わないか
対象は白書1冊・数百ページで、チャンク数はたかだか800件規模（実測723件）。
numpyの行列積は800×1536次元でもミリ秒オーダーで終わり、インデックス構築や
プロセス管理の複雑さを払ってまで外部DBを導入する理由がない。この判断自体を
レポートの論点にしている。

### チャンク分割（`src/chunker.py`）
固定長分割にしなかった理由は、Q07のような「複数章にまたがる相談型の質問」で
章の途中で文脈が寸断されたチャンクしか検索に引っかからず、指導員が読んでも
話の筋が追えない回答になってしまうため。以下の優先順位で階層的に分割する。

1. 章・節（`pdf_loader.py` が確定させた `section`）が変わる境界を最優先の区切りとする
2. 節の中身が `CHUNK_SIZE` を超える場合のみ段落単位で貪欲に詰め直す
3. 1段落だけで超える場合のみ文単位（句点「。」を優先境界とする）に分解する
4. それでも1文が超える場合（句点のない数値の羅列など）に限り、最後の手段として
   文字数で機械的に切り、`CHUNK_OVERLAP` 分だけ重複させる

overlapは手順4の文字数分割にしか使わない。段落・文の単位はそれ自体で意味の
まとまりを保っているため、そこに重複を挟んでもコストと検索ノイズが増えるだけと判断した。

### PDF解析（`src/pdf_loader.py`）の実データ対応
対象PDFをブロック座標レベルで調べたところ、単純な `get_text()` の文字列連結では
章節ラベルもページ番号も正しく拾えないことが分かった。

- 章・節見出しは本文とは別ブロックだが、見開きページのレイアウトをミラーしており
  「マーカー→タイトル」と「タイトル→マーカー」の順序が反転する
- 右マージンに同じ見出しを1文字ずつ縦に並べた飾りブロックが重複して存在する
- ページ番号はページ下部の孤立した数字ブロックとして、左右どちらかの余白に出る
- 段落の区切りはブロック境界ではなく「段落先頭の全角スペース」で示される
  （1ブロック＝1行であり、1ブロック＝1段落ではない）

これらを空白除去済み文字列への前方一致・後方一致の両方向マッチ、本文カラム外
（x1>540pt）のブロック除外、全角スペースによる段落判定、という3つのルールで解決した。
詳細は `src/pdf_loader.py` のモジュールdocstringを参照。

### 検索方式（`src/retriever.py`）
3方式とも自作し、`SEARCH_MODE` で切り替えられる。

- **ベクトル検索**: クエリを埋め込み、L2正規化済み行列との内積をnumpyで一括計算。
  内積＝コサイン類似度になるよう保存時に正規化している。
- **BM25**: 形態素解析器を使わず**文字bi-gram**でトークン化した自作BM25
  （k1=1.2, b=0.75）。解析器の依存を増やすとDocker環境・Streamlit Cloud双方の
  構築が重くなるため、依存ゼロで「てにをは」の揺れに頑健な文字bi-gramを選んだ。
- **ハイブリッド**: RRF (Reciprocal Rank Fusion) で順位を統合する
  （`score = Σ 1/(60+rank)`）。スコアの絶対値は方式間で比較できないため、
  順位だけを使って統合する。

3方式のスコアはスケールがバラバラ（コサイン類似度[-1,1]・BM25生スコア（無制限）・
RRFスコア（小さい値））なので、`MIN_SCORE_THRESHOLD` で横並びに比較できるよう
0〜1に正規化して返している。vectorはコサイン類似度そのもの、BM25は
「そのクエリの理論上の最大値（Σ idf(t)×(k1+1)）」で正規化した値、hybridは
RRFで順位を統合しつつ、返すスコアには実際の関連度を表すコサイン類似度
（無ければBM25側のスコア）を使う。詳細と、この設計に至った経緯（評価実行で
見つかった不具合）は次項を参照。

### 閾値による構造的な拒否（Q09対策）
検索結果の最高スコアが `MIN_SCORE_THRESHOLD`（既定0.30）未満の場合、
**LLMを呼ばずに**「資料内に該当する記述が見つかりませんでした」を返す
（`src/generator.py`）。プロンプトでの指示（「わからなければ答えるな」）は
モデルが従わないことがあるが、コードのif文による閾値チェック自体は100%決定的に働く。

ただし「決定的に働く」のは、そこに渡すスコアが正しく関連度の低さを表している
場合に限られる。実際に `eval/run_eval.py` を実行してこの前提を検証したところ、
不具合が見つかった。BM25/ハイブリッド(RRF)のスコアを「そのクエリでの実績最大値・
順位」だけで正規化していた実装では、範囲外質問（Q09: 観光業について）でも
候補の中の誰かが機械的に最高スコア（1.0近辺）になってしまい、**BM25とハイブリッド
の両方で一度も閾値ゲートが発動しなかった**（範囲外質問なのにLLMが呼ばれ、
たまたまプロンプトの指示に従って正しく拒否していただけだった）。

これを受けて、BM25のスコアは「実績最大値」ではなく「理論上の最大値
（Σ idf(t)×(k1+1)、tf→∞での収束値）」で正規化するよう修正し、ハイブリッドの
信頼度スコアにはRRFの順位スコアではなく実際の関連度を表すベクトルのコサイン
類似度（無ければBM25の理論上限正規化スコア）を使うよう設計を変更した
（`src/retriever.py`）。修正後、BM25モードはQ09を正しく拒否できるようになった。
一方でベクトル・ハイブリッドは、同じ「人材不足」という語彙が業種を問わず
出現するためコサイン類似度が0.4程度まで上がり、閾値0.30だけでは防ぎきれない
ままだった（詳細は下記の評価結果、および既知の限界を参照）。
**閾値ゲートは唯一の防御ではなく、プロンプト内の拒否指示と合わせた多層防御**
として設計している。

### 図表の扱い（Phase 8）
図（グラフ）と表（表組み）は性質が違うため、別々の方針を取っている。

- **図**: ほぼベクター描画のグラフでラスター画像を持たないため、マルチモーダル
  LLMによるキャプション化はしていない（画像自体に意味情報が乗っていない）。
  代わりにテキスト抽出時に残るキャプション文字列（例:「図110-7 第一次所得収支の推移」）を
  正規表現で拾い、チャンクのメタデータ（`figures`）として保持している。
- **表**: PyMuPDFの `find_tables()` で検出し `to_markdown()` でMarkdown化して
  ページ本文に追加している（`src/pdf_loader.py`）。素朴に使うとグラフの目盛り・
  凡例も罫線なしの格子状に並ぶため表と誤検出する問題があり、セルの非空率が
  0.6未満の検出結果を捨てることで本物の表組みだけを拾っている（実データで
  本物の表は非空率0.7〜1.0、グラフの誤検出は中央値0.44程度と分布が分かれることを確認済み）。
  実データで70ページから本物の表組み（価格交渉の実施状況、生成AI活用事例、
  企業概要カードなど）を検出できている。

UIでの出典表示にも使っている。実際の検索精度への効果測定は本番APIキーでの
評価実行が必要（`eval/run_eval.py` の実行結果を参照）。

### 見つかった不具合: グラフの数値が本文段落を汚染していた問題

「中小企業の賃上げ状況は？」という質問を1件、PDF読込から回答生成まで手動で
トレースして検証していたところ、実際のバグを発見した。

- retrieverは正解ページ（p80）のチャンクを全方式で1位に検索できていたが、
  LLMの最終回答はその核心情報をほぼ無視し、「資料内に該当する記述が見つかりません
  でした」という誤った言い訳を返していた
- 原因を実験で切り分けたところ、モデルの性能や指示文の問題ではなく、
  **検索がそもそも必要なチャンクを拾えていなかった**ことが判明（該当チャンクを
  強制的に文脈に追加すると、LLMは正しく回答できた）
- さらに遡ると、罫線の無い棒グラフの軸目盛り・凡例テキストが、段落判定
  （全角スペースの有無）をすり抜けて直前の文章段落に連結され、1文（141字）が
  903字に膨れ上がり、chunker.pyの文字数フォールバック分割で前後の文脈から
  切り離された孤立チャンクになっていた、というのが真因だった

**修正**: 文字の大半（5割超）が数字・記号のブロックは、本文から除外する
（`_is_mostly_numeric`、`src/pdf_loader.py`）。当初「独立した段落にするだけ」の
実装を試したが、chunker.pyの貪欲パッキングがすぐ隣の文章段落と再結合して
しまい不十分だったため、「除外する」方針に変更した。

**修正の効果**（実測）: BM25で該当チャンクの検索順位が10位→3位に上昇。
生成される最終回答から誤った「見つかりません」という言い訳が消え、正しい
数値・中小企業限定のデータを引用するようになった（vector/bm25/hybrid全方式で確認）。

この一連の調査（検索の成功≠回答の成功を実際に踏む→仮説を実験で検証→
PDF解析まで遡って根本原因を特定→修正→再検証）は、詳細を
`notes/session_log.md`（gitignore対象）に記録している。

## セットアップ

Docker前提（`.devcontainer/`）。Python 3.12固定（Streamlit Cloudとの互換性のため
3.13以降は使わない）。バージョン指定は`.python-version`（Streamlit Cloudが
パッケージ管理に使う`uv`が読む）と`runtime.txt`（Heroku形式。他ホスティング向けの
保険）の2箇所に書いている。`.python-version`が無いと、`uv`はデフォルトで
最新のPythonを使ってしまい、`pillow`等のビルド済みパッケージが存在せず
ビルドエラーになる（実際にStreamlit Cloudへの初回デプロイで発生し、追加した）。

```bash
# 依存関係のインストール（devcontainer内は postCreateCommand で自動実行される）
uv venv --python 3.12
uv pip install -r requirements.txt

# .env に OPENAI_API_KEY を設定（.env.example を参照）
cp .env.example .env

# PDF読込→チャンク分割→埋め込み生成を一括実行（初回のみ、数分かかる）
python scripts/build_index.py

# チャットボットを起動
streamlit run app.py
```

### Streamlit Cloudへのデプロイ

1. 本リポジトリをGitHubにpushする（`data/raw/*.pdf` はサイズが大きいがpublicな
   政府文書なので追跡している。`data/processed/` は再生成できる中間ファイルなので
   `.gitignore` で除外している）
2. Streamlit Cloudでアプリを作成し、Secretsに `OPENAI_API_KEY` と `APP_PASSWORD` を設定する
   （`APP_PASSWORD` はPublic公開時にOpenAI APIの課金を伴う呼び出しを誰でもできて
   しまうのを防ぐための簡易な共有パスワード。閲覧者ごとのメールアドレス管理を
   避けるため、Streamlit Cloudの個別アクセス制限ではなくアプリ側の1個の
   パスワードにしている。未設定だと誰でもアクセスできてしまうので必ず設定する）
3. 初回起動時、インデックス未構築の画面が出るので「インデックスを構築する」ボタンを押す
   （Streamlit Cloudはターミナルを持たないため、`scripts/build_index.py` と同じ処理を
   アプリ内から1回だけ実行できるようにしている）

### テストの実行

```bash
uv pip install -r requirements-dev.txt
pytest tests/
```

OpenAI APIキーが無くても実行できる範囲（PDF解析・チャンク分割・BM25/RRF・
閾値ゲート・評価スクリプトの集計ロジック）を51件のテストでカバーしている
（`tests/`）。ベクトル検索・LLM呼び出しはモックして検証しており、実際の
埋め込み生成・回答生成そのものはAPIキー投入後に手動で確認する。

### 評価の実行

```bash
python eval/run_eval.py
```

`eval/eval_questions.py` の10問を vector/bm25/hybrid の3方式で実行し、
`eval/results/eval_detail.csv`（質問ごとの詳細）と
`eval/results/eval_summary.md`（方式×指標の比較表）を出力する。
`expected_points`（論点を満たしたか）と `must_not`（幻覚がないか）は
文章の意味を読む必要があり自動判定が信頼できないため、判定欄を空欄で
出力し目視で埋める前提にしている（目視判定は実施・確定済み。
再実行すると判定欄は空欄に戻るため、再実行する場合は先に結果をコピーすること）。

#### 実行結果（gpt-4o-mini, text-embedding-3-small）

| 検索方式 | 検索成功率（9問中） | 論点一致率（目視） | 幻覚検出件数（目視） | 範囲外質問の正答拒否率 |
|---|---|---|---|---|
| vector | 100% | 78%（7/9） | 1/9 | 100%（1問中） |
| bm25 | 89% | 56%（5/9） | 0/9 | 100%（1問中） |
| hybrid | 89% | 56%（5/9） | 0/9 | 100%（1問中） |

サンプル数が少ない（対象9問・範囲外質問1問）ため統計的な結論ではなく、
傾向の確認として読む前提だが、以下3点は実装の設計判断に直結する発見だった。

- **Q07（複数章にまたがる相談型質問）はvectorのみ正解、bm25/hybridは失敗した。**
  「人手不足に悩む中小製造業がDXを進めつつ人材も確保したい」という複合的な
  自然文クエリは、期待ページ（よろず支援拠点のp278、DX人材育成支援コーナーの
  p287）と完全一致する語彙が少なく、文字bi-gramのBM25では拾いきれなかった。
  ハイブリッドもBM25側の悪い結果に順位を引っ張られて失敗した。vectorも実際には
  p278の支援策しか引けておらず、論点一致率で見ると「複数章の統合」までは
  できていない（`expected_points_met`=FALSE）。→ 複合質問はベクトル検索が
  相対的に強いが、クエリ分解なしでは複数章の統合までは解決しないという
  より正確な結論になった。
- **Q09（範囲外質問）で、BM25/ハイブリッドのスコア正規化に不具合を発見・修正した。**
  詳細は「閾値による構造的な拒否」の項を参照。修正後、BM25は正しく拒否できる
  ようになったが、vector/hybridは「観光業の人材不足」という業種違いだが語彙の近い
  質問までは閾値だけでは防ぎきれないことが分かった（意味的類似度と話題の妥当性は
  別物、という現実的な限界）。ただし結果的にはLLM自身が「見つかりません」と
  正しく答えており、3方式とも最終的な回答としては範囲外質問に正答している。
- **bm25の論点一致率が22%（2/9）と極端に低かったのは、検索精度の問題ではなく
  閾値ゲートの誤爆が原因だった。** 範囲内9問中6問（Q01,03,05,06,08,10）で
  期待ページは上位5件に入っている（`source_hit`=TRUE）のに、BM25の正規化
  スコアがvector/hybrid共通のMIN_SCORE_THRESHOLD(0.30)に届かずLLMが呼ばれて
  いなかった。つまりBM25は「検索はできているが、スコアのスケールが閾値と
  噛み合っていない」状態だった。評価用10問で方式ごとのスコア分布を実測した
  ところ、vector/hybridは範囲内最低0.43・範囲外0.47で閾値0.30の位置はそのままで
  問題ないが、bm25は範囲内最低0.17・範囲外0.13と全体にスコアが低く、0.30という
  共通閾値はbm25にとって厳しすぎることが分かった。→ `MIN_SCORE_THRESHOLD`を
  方式ごとの辞書に変更し、bm25だけ0.15（範囲外0.13と範囲内最低0.17の中間）に
  下げて再評価した。結果、bm25の論点一致率は22%→56%（2/9→5/9）に改善し、
  幻覚の増加（`must_not_violated`）は0件のままだった。根拠となるスコア実測値は
  `src/config.py`のコメントに記録している。

#### 評価の限界と対処案

現時点の評価（10問、目視判定確定済み）が測れていること・測れていないことを
明記する。今後、質問を追加した場合は、上の結果表とこの節を更新する。

| 評価の観点 | 現状 | 限界 | 対処案 |
|---|---|---|---|
| 精度 | 検索成功率（自動）に加え、回答の論点一致率を目視判定済み（`expected_points_met`）。bm25の閾値誤爆は方式別の閾値再調整で対応済み | 判定者が開発者自身であり客観性に限界がある | 第三者レビュー |
| カバー率 | 質問の種類（単一トピック・図表の数値・複合質問・範囲外）を分けて設計 | 10問・白書1冠では文書全体のカバー率は測れない | 質問数を増やし、章・節単位でのカバーを確認する |
| 幻覚の頻度 | 閾値ゲート・プロンプト・出典表示・画面の注意書きで構造的に抑制。`must_not_violated`を目視判定済み | 検出件数は vector 1/9（Q07の不完全な統合）のみで、bm25/hybridは0/9。範囲外質問は1問のみで拒否率の統計的信頼性は低い | 範囲外質問・意図的に誤誘導する質問を増やす |
| 質問の偏り | 文書を知る者が10問を作成 | 実際の相談より易しい可能性がある | 実際の相談に近い質問を追加し、調整用と評価用に分ける |
| ばらつき | 1回ずつの実行 | LLMの揺れを見ていない | 複数回実行して確認する |

**BLEU・RAGASを導入していない理由**: BLEUは単語の重なりで比べるため、同じ意味でも
言い回しが違えば低く出て、自由記述の質問応答では実態を反映しにくい。RAGASはLLMに判定させる
ため、スコアの根拠を自分で説明しにくく（このプロジェクトが避けてきたブラックボックス化）、
評価にも別のLLM呼び出しの費用がかかる。10問の規模では目視判定で足りると判断した。
質問数が増えた場合は、RAGASのFaithfulness（回答が文脈に忠実か）の導入を検討する。

## 業務的示唆

想定ユースケース（商工会議所の経営指導員による中小製造業への支援）を前提に、
このシステムが貢献しうる業務効果を整理する。

- **面談準備時間の短縮**: 数百ページの白書から該当箇所を探す作業を、
  質問文を打つだけの検索に置き換える。面談直前の「この業界の最新動向は？」
  といった駆け込み確認に使える。
- **提案の裏付け強化**: 経営指導員の経験則だけでなく、白書の章・ページを
  明示した根拠付きで支援策を提示できるため、相談者（中小企業経営者）への
  説明の説得力が増す。
- **面談メモ作成コストの削減**: メモ下書きタブにより、相談内容から関連する
  白書の記述・提案できる支援策・要確認事項を自動で下書きできる。ゼロから
  メモを書き起こす時間を圧縮できる。
- **誤案内リスクの低減**: 閾値ゲートにより、白書に根拠がない質問には
  「わからない」と答える設計にしているため、経営指導員が誤った情報を
  相談者に伝えてしまうリスクを構造的に下げている。

一方で、次の留意点がある（意思決定者に必ず伝えるべき事項）。

- **対象は令和5年度版のみ**: 白書は年次更新されるため、翌年度以降は
  再インデックスが必要。「最新の統計かどうか」をこのシステムだけでは判断できない。
- **一次情報としては使えない**: 生成AIの回答はあくまで白書の要約・引用であり、
  法的助言や正式な行政手続きの判断材料としては、必ず原本（白書PDF）を
  経由した確認が必要。
  この注意は画面上にも常時表示している（`app.py`の`DISCLAIMER`、チャット・
  メモ下書き両タブの上部）。
- **機密情報は扱っていない**: 対象データは公開文書のみ。実際の相談内容
  （企業名・財務情報等）をこのシステムに入力する運用にする場合は、
  OpenAI APIへの送信データの扱い（学習利用の有無、保持期間）を
  別途確認する必要がある。

## 既知の限界

- **章節ラベルの粒度がページ単位まで**: `section`はページ単位でしか追跡していないため、1ページの
  中に節の境界がある場合、そのページ全体が最後に検出した節のラベルになる。前半が別の節に属する
  文章でも、出典の章節が後の節として表示されうる。実際に何ページで起きているかは未検証。
  対処案: 見出しが更新されるたびに区切りを記録し、ページ単位ではなく段落単位で`section`を持たせる
- **リランキングは未実装**: 現在のハイブリッド（RRF）は、ベクトル検索とBM25の**順位を合体**する
  方式で、質問とチャンクをペアで読み直して採点し直すリランキング（cross-encoder等）ではない。
  導入する場合は、候補（上位20件）を採点し直して上位k件を選ぶ。コストと遅延が増え、効果は未測定
- **クエリリライト・会話履歴は未実装**: 質問は毎回単独で扱い、過去のやり取りは検索・生成に反映しない
  （画面に履歴を表示するだけ）。対処案: 履歴を踏まえて質問を単体で意味が通る形に書き換える
- **対象年度**: 令和5年度版のみを対象としており、それ以降の政策変更は反映されない
- **グラフの視覚的な傾向は読み取れない**: 図表はベクター描画のためOCR/画像認識は
  行っていない。当初はグラフの軸ラベルや凡例の生数値が本文段落に混入し、
  検索精度を下げるバグがあったが修正済み（後述の「見つかった不具合」参照）。
  現在は軸目盛りの生数値は本文から除外し、キャプションのみメタデータとして
  保持している。「右肩上がりの傾向」のような視覚的な読み取りはできない
- **大きすぎる表は文字数分割で崩れうる**: 表（罫線付き表組み）はMarkdown化して
  いるが、1つの表がCHUNK_SIZE（600字）を超える場合、文単位（句点区切り）でも
  収まらなければ最終手段の文字数分割に落ち、Markdownの行の途中で切れる可能性がある。
  実データでは大半の表が案件カード程度の大きさに収まり問題は顕在化しなかったが、
  行単位で分割する専用ロジックは未実装
- **見出し誤検出**: 目次ページ自体や「表彰制度」章の一部箇条書きで、短い
  見出し様の文字列を章・節ラベルとして誤検出することがある（本編の章・節
  ラベルには影響しないことを実データで確認済み。詳細は `src/pdf_loader.py` docstring）
- **脚注**: ページ右マージンに配置された脚注（本文カラム外, x1>540pt）は
  ノイズ除去のロジックにより本文から除外されるため、検索・回答の根拠には使われない
- **複合的な相談型質問はBM25/ハイブリッドが弱い**: 評価実行で判明。単一トピックの
  質問（Q01〜Q06、Q08、Q10）は全方式で高精度だったが、2つの支援策にまたがる
  Q07はvectorのみ正解し、文字bi-gramのBM25（およびそれに引っ張られるhybrid）は
  失敗した。今後の改善案としては、質問をトピックごとに分解して個別に検索し
  結果を統合する「クエリ分解」が考えられる（未実装）
- **閾値ゲートは意味的に近い業種違いの質問までは防げない**: 「観光業の人材不足」
  のような、話題は近いが対象外の質問は、ベクトル検索のコサイン類似度が0.4程度まで
  上がり、MIN_SCORE_THRESHOLD（0.30）だけでは拒否しきれない。BM25は評価実行で
  見つかった正規化の不具合を修正済み（実績最大値ではなく理論上限で正規化）だが、
  vector/hybridの信頼度はコサイン類似度に依存するため、この限界は残っている。
  プロンプト内の拒否指示との多層防御で運用している
